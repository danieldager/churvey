## 09:45 — Root-caused the diacritics bug. It was never a font problem.

Daniel reported mojibake across the doc. The file was fine: valid UTF-8, "Île-de-France" stored
as U+00CE correctly, no double-encoding signatures anywhere.

**The cause is in the artifact wrapper.** It emits its frame-runtime `<script>` block, several
thousand bytes of it, BEFORE `<meta charset=utf8>`. The HTML spec has browsers scan only the
**first 1024 bytes** for an encoding declaration, so the charset lands far outside that window
and is ignored. The browser falls back to a legacy single-byte encoding and every accented
character breaks. Not something a `<meta>` of our own could fix, since ours would be even
further down the document.

**Fix: make the document pure ASCII.** Non-ASCII in markup becomes numeric character
references, non-ASCII inside `<script>` becomes `\uXXXX` escapes (entities are not parsed in
script content, so the two halves need different treatment). Both are encoding-independent.

Verified the hard way: served the file over a local server sending **no charset at all**, the
exact failure mode, and every accent renders correctly. "LA RÉUNION", "J'habite à Sauze. Faut-il
présenter une pièce d'identité", "À la mairie du Havre, 1517 place de l'Hôtel-de-Ville",
"Christophe Béchu", "Répertoire national des élus", "Ministère de l'Intérieur", and the Paris
tooltip's "1er–4e · 5e · 6e …". Byte check: file is 100% ASCII and decodes identically as
windows-1252.

**Caveat for whoever regenerates this page:** the ASCII escaping is a post-processing step, not
part of a generator. If the map data or any copy is rebuilt, re-run it or the mojibake returns.

Also removed the zoom instructions from the map, per Daniel, since they shrank the plot area.
The +/-/Reset buttons stay and scroll/drag still work.

Confirmed: the 168 ambiguous communes are excluded, frame 34 383, and no answer in the
